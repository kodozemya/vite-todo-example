# Приклад: Проєкт на Vite

Живе демо: https://vite-todo-example-theta.vercel.app/

Еталонний розв'язок Арени модуля **«Кузня Бандлів»** (Збірка та інструменти).
Той самий «Список справ», що й у [`js-todo-example`](https://github.com/kodozemya/js-todo-example),
але зібраний Vite, розбитий на модулі й покритий тестами.

Макет: [ToDo list](https://www.figma.com/design/33vXaYMe6v0WHUgSLqwFGB/ToDo-list?node-id=0-1)

> Це приклад, а не шаблон. Порівняй його з `js-todo-example`: саме різниця
> між ними і є змістом цієї Арени.

## Як запустити

Потрібен Node.js 22.12 або новіший: цього вимагають Vite 8 і Vitest
(перевір командою `node -v`).

```bash
npm install     # поставити залежності: Vite, Vitest і jsdom
npm run dev     # сервер розробки з миттєвим оновленням, http://localhost:5173
npm run build   # зібрати продакшн-версію у теку dist/
npm run preview # подивитися на зібране як на справжньому сервері
npm run test    # один прогін тестів (vitest run)
```

## Що змінилося порівняно з версією без збирача

| | `js-todo-example` | `vite-todo-example` |
| --- | --- | --- |
| Запуск | відкрити `index.html` | `npm install && npm run dev` |
| Код | один `app.js` | п'ять модулів у `src/` |
| Стилі | `<link>` у розмітці | `import "./style.css"` у `main.js` |
| `<script>` у HTML | сам застосунок | лише точка входу `/src/main.js` |
| Продакшн | ті самі файли | `dist/` з мініфікацією й хешами в іменах |
| Тести | немає | `npm run test`, Vitest |

## Структура

```
index.html          розмітка; єдиний <script> це точка входу
vite.config.js      налаштування Vitest (оточення jsdom)
src/
  main.js           з'єднує модулі: елементи, підписки, події
  state.js          список справ і єдиний спосіб його змінити
  state.test.js     тести на чисті функції зі state.js
  storage.js        читання й запис у localStorage
  render.js         перетворення списку на розмітку
  focus.js          фокус після видалення; вантажиться окремим чанком
  style.css         стилі за макетом
```

Межі між модулями проведені не навмання, а за питанням
**«що зміниться, якщо…»**:

- Список поїде на сервер замість localStorage: зміниться **тільки** `storage.js`.
- Зміниться макет: **тільки** `render.js` і `style.css`.
- З'явиться фільтр «показати лише невиконані»: **тільки** `main.js`,
  бо він і так вирішує, що передати в `renderTasks`.

Якщо зміна вимоги зачіпає три файли з чотирьох, межі проведені неправильно.

## Тести

`state.js` тримає список у змінній модуля, а таку змінну тестувати незручно:
кожен тест бачив би те, що залишив попередній. Тому вся логіка списку винесена
в три чисті функції, `withTaskAdded`, `withTaskToggled` і `withTaskDeleted`.
Вони беруть масив і повертають новий, а `addTask`, `toggleTask` і `deleteTask`
лише викликають їх, зберігають результат і перемальовують сторінку.

Тести в `src/state.test.js` перевіряють ці функції: додавання, порожній рядок,
перемикання туди й назад, видалення, а також те, що вхідний масив лишається
незмінним. `state.js` імпортує `storage.js`, а той звертається до `localStorage`,
тому у `vite.config.js` стоїть `environment: "jsdom"` і встановлено пакет `jsdom`.

## Продуктивність

- **Окремий чанк.** Код, що переводить фокус після видалення справи, лежить у
  `src/focus.js`, і `main.js` підвантажує його через `import("./focus.js")`
  лише після кліку по хрестику. Після `npm run build` у `dist/assets/` видно
  окремий файл `focus-*.js` поруч з `index-*.js`.
- **Шрифт.** Inter підключено з Google Fonts з параметром `display=swap`:
  це той самий `font-display: swap`, тільки його дописує Google у свій CSS.
  Поки шрифт вантажиться, текст видно системним шрифтом. Запасний стек у
  `--font` (`system-ui` та інші) близький до Inter за метриками, тому під час
  підміни верстка не стрибає.
- **Зображення.** Їх у проєкті немає: хрестик це символ ✕, а чекбокс
  намальований CSS. Якби вони були, кожному `<img>` треба було б задати
  `width` і `height`.

### Звіт Lighthouse

Перевіряй зібрану версію, а не сервер розробки:

```bash
npm run build
npm run preview   # http://localhost:4173
```

Відкрий цю адресу в Chrome, далі DevTools → вкладка Lighthouse → Analyze page load.

## Що перевіряє ментор

- Проєкт лежить у новому репозиторії, а не в тому, де лежить застосунок
  з Арени модуля про JavaScript.
- Після `npm install` команда `npm run dev` піднімає сервер без помилок у терміналі.
- `npm run build` завершується успішно й створює теку `dist`.
- Усі дії застосунку працюють так само, як до перенесення: додавання,
  видалення й позначка «виконано».
- Код розбито щонайменше на два модулі, пов'язані через `import`/`export`.
  У HTML одна модульна точка входу, внутрішні модулі не підключаються
  окремими classic-script тегами.
- У репозиторії немає ані `node_modules`, ані `dist`.
- `package.json` і `package-lock.json` закомічені.
- `README.md` містить команди запуску, і вони справді працюють на чистій
  копії репозиторію.
- У проєкті є скрипт `test` і щонайменше 3 тести на винесений модуль,
  `npm run test` проходить.
- У `README.md` є скрин звіту Lighthouse; зображення мають задані розміри,
  власні webfont мають `font-display`. Код, який не потрібен одразу, винесено
  в окремий чанк через динамічний `import()`.

## Чому так

**Модулі справді розділені, а не просто розкладені по файлах.**
`state.js` не звертається до `document`. `render.js` не імпортує `state.js`,
список приходить йому аргументом. Чотири файли, що всі імпортують одне одного,
це той самий один файл, тільки з чотирма вкладками.

**`package-lock.json` комітиться обов'язково.** `node_modules` і `dist` лежать
у `.gitignore`: перша тека відновлюється з `package-lock.json` однією командою,
друга збирається з вихідників. Без lock-файла `npm install` у ментора може
поставити інші версії, ніж у тебе, і «в мене працює» стане правдою в буквальному сенсі.

**Стилі підключає JavaScript, а не `<link>`.**
`import "./style.css"` у `main.js` виглядає дивно, поки не подивишся у `dist/`:
Vite бачить стилі у графі імпортів, мініфікує їх і дає файлу ім'я з хешем
(`index-BTCCognu.css`). Хеш змінюється разом із вмістом, тому браузер
користувача не покаже старий кеш після оновлення сайту.

## Як здати

Перший коміт роби одразу зі згенерованого шаблону Vite, а всю свою роботу
веди в окремій гілці, наприклад `feature/vite-migration`. Комітів може бути
кілька: перенесення коду, тести, продуктивність. Так ментору легше читати
зміни по кроках. Потім відкрий pull request до `main` і надішли посилання
ментору. В описі PR коротко напиши, що переніс, як запустити проєкт і тести,
і додай скрин Lighthouse або посилання на нього в README.
